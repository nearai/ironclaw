# Brand principles

What IronClaw believes, in order. Everything downstream — UI copy, motion,
feature defaults, marketing — should be checkable against these. The
sibling page, **Voice & copy**, is these principles cascaded into concrete
UI-copy rules.

<Callout title="This repository is the source of truth">
  Per the design review (Jul 21), this repo is the single source of truth
  for design principles and living documentation. These pages are plain
  markdown: edit them here, in a PR, like any other change. The
  principles are written to be as correct and thorough as we can make

## 1. Wow — impress out of the gate

The first session has to feel like the future arrived. Not a tour, not a
setup wizard — a real result the user didn't ask for yet.

- **The demo is the product.** Within minutes of connecting a tool, the
  agent should have derived something true and useful from the user's
  actual world ("34 newsletter threads are burying your real mail") and
  acted on it. Show, don't claim.
- **No value behind a gate.** Sign-up, payment, and configuration are
  deferred until the user has already seen the agent work.
- **Craft is part of the wow.** Motion, typography, and finish signal
  "this was built by people who care" before a single word is read.
- **One magic moment beats ten features.** First-run flows optimize for
  a single unforgettable proof, not coverage.

## 2. Trust — credible at first glance, compounding over time

Trust runs on two clocks, and we design for both.

- **Instant credibility.** Plain language, visible security posture
  (the secrets vault — `crates/ironclaw_secrets`; sandboxed execution —
  `crates/ironclaw_process_sandbox`; policy-gated egress —
  `crates/ironclaw_runtime_policy` and `crates/ironclaw_network`), calm
  status colors, no dark patterns. A first-time visitor should be able
  to see *why* it's safe, not just be told.
- **Compounding trust.** Every action leaves a receipt: an activity
  feed, run logs, previews of anything that leaves the system, one-click
  undo. The agent narrates what it did and why. Failures are stated
  plainly, with the fix — never hidden, never dramatized. (The receipt
  surfaces are the design target the workspace builds toward; approval
  flows live in `crates/ironclaw_approvals`.)
- **The trust envelope grows.** As receipts accumulate, users grant the
  agent more autonomy. Trust isn't asked for; it's earned and then
  spent carefully. This is design intent for how autonomy scales, not a
  claim that a single enforcing mechanism ships today; the pieces that
  exist are cited above.

## 3. Automate — do the AI thing

IronClaw is proactive. It derives routines from the user's world —
inbox, calendar, repos, chats — and sets them up without waiting to be
asked. It does not nag for permission inside the trust the user has
granted; the user's core principles (productivity, security, privacy)
are baked into what it chooses to automate and how. Where that trust has
not been granted yet, it suggests instead of acting.

- **Act, then show your work.** The default posture is "I did this, and
  here's why" — not "may I?". Asking permission for routine work is a
  product failure: it hands the busywork back to the user.
- **Guardrails, not permission prompts.** Everything the agent does is
  visible, reversible, and tunable — *Review*, *Adjust*, *Pause*,
  *Undo*. Safety lives in the receipts and the undo, not in
  confirmation dialogs.
- **Principles baked in.** Derived routines optimize for the user's
  time and attention, and respect the security boundary by
  construction: credentials stay sealed in the vault, data goes only to
  allowlisted endpoints.
- **Human in the loop, always.** The agent is a tool for user-driven
  outcomes, not an autonomous actor with its own agenda. Autonomy is
  something the user grants, watches through receipts, and can revoke in
  one click. Inside the granted envelope the agent acts and shows its
  work; outside it, the agent suggests the action and waits. Proactivity
  and human-in-the-loop are not opposites here: the loop is the receipts,
  the steering verbs, and the envelope, not a confirmation dialog in
  front of every step.
- **The boundary that remains.** Irreversible external actions — money
  leaving, sending as the user to someone new, sharing data with a new
  party — still get explicit consent (the approval pipeline in
  `crates/ironclaw_approvals` is where these gates are enforced).
  Autonomy applies inside the trust envelope the user has granted
  (see #2); the envelope grows, the consent moments shrink.

## 4. Channel-first — meet the user where they already are

The differentiating posture from the design review: optimize for the
channels where the user already works (chat, email, Slack, the terminal),
not for pulling them into our surfaces. The dashboard is the record, not
the destination.

- **Just-in-time, not just-in-case.** Insights arrive in the moment and
  place they're useful ("your 10:00 call moved, I shifted your prep
  block"), instead of waiting on a dashboard visit. Value is predictive
  and workflow-shaped, not a chart the user has to go read.
- **The workspace is the receipt.** The app remains the place to review,
  adjust, and audit what the agent did. It earns visits through the
  activity feed and run detail, not through information held hostage.
- **Every surface stands alone.** A message in Slack or email carries the
  finding, the action taken, and the escape hatch by itself. No "open the
  app to see more" as a default. Standing alone is about completeness,
  not volume: payloads go only to channels the user connected and
  authorized, carry the minimum data the finding needs (external
  channels are untrusted transport — summarize, don't dump), and any
  privileged action linked from the message still authenticates on our
  side.

## 5. Private and secure — enterprise-grade, by construction

Privacy and security are named principles, not implementation details,
because enterprise adoption depends on them being legible.

- **Private by design.** The user's data is theirs. Credentials stay
  sealed in the vault, work happens in encrypted enclaves, and outbound
  traffic is limited to allowlisted endpoints. These are architectural
  facts we can show, not policy promises we ask people to believe.
- **Legible security.** The security posture is visible in the product:
  what's connected, what's sealed, what left the system and where it
  went. A security review should be able to answer itself from the UI.
- **Data minimalism.** The agent reads what the routine needs and no
  more. Scope is granted per tool, shown plainly, and revocable.

## 6. Human, plain-spoken

The tone is soft and human — closer to how Claude's product copy reads
than to edgy tech branding. Confident without being loud; technical
truth in the user's words. No exclamation-mark enthusiasm, no
alarm-speak, no jargon where a plain word exists.

## How they cascade

| Principle | Product behavior | Copy behavior |
|---|---|---|
| Wow | Real derived result in the first session | Lead with the specific finding, not the feature name |
| Trust | Receipts: feed, logs, previews, undo | Narrate actions in past tense with the reason; state failures plainly |
| Automate | Acts inside the granted envelope, suggests outside it | "I set this up — adjust or undo" inside; "I can set this up — want it?" outside |
| Channel-first | Insights delivered in the user's channels, just in time | Each message self-contained: finding, action, escape hatch |
| Private & secure | Vault, enclaves, allowlists, per-tool scopes shown in the UI | State the architectural fact plainly; never "trust us" |
| Human | Calm defaults, no dark patterns | Sentence case, short verbs, the user's vocabulary |

The concrete UI-copy rules that fall out of this table live in
**Docs → Voice & copy**.
