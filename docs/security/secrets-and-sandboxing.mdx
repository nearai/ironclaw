The [Security overview](/security) states the rule that models and tools should never see your raw credentials. This page is how that rule actually holds — where secrets live, how one reaches an outbound request without ever entering a tool's memory, and where the guarantee stops.

This page is for anyone deciding whether to trust IronClaw with a credential. If you are *building* a tool — manifest fields, limits, host functions, installation — the reference is [WASM Tools](/capabilities/sandboxed-tools).

---

## Where Secrets Live

Your stored credentials are encrypted at rest in IronClaw's secret store. They are decrypted only inside the host process, only for the duration of a single authorized invocation, and the URL and header values that carried the plaintext are zeroized when each request ends.

### The Master Key

A single **master key** unlocks the secret store. On startup IronClaw resolves it in this order:

<Steps>
  <Step title="Cached key file">
    `.reborn-local-dev-secrets-master-key` under the runtime's storage root, created with owner-only (`0600`) permissions. Once a key exists here it wins, so the store is never accidentally re-keyed on a later boot.
  </Step>

  <Step title="`SECRETS_MASTER_KEY` environment variable">
    Used when there is no cached key file, and then written to that file. Any value of at least 32 bytes with at least 8 distinct byte values; the conventional choice is the 64-character output of `openssl rand -hex 32`, which is used as-is — hex is not decoded. This is the path for Docker, CI, and air-gapped deployments where you supply the key explicitly.
  </Step>

  <Step title="OS keychain">
    macOS Keychain or the Linux secret service. The preferred local path — `ironclaw onboard` provisions a key here when no key file exists yet and the keychain is reachable, stored under your account, never written to disk in plaintext. A keychain hit is used as-is and is deliberately *not* copied to the key file; the two are alternatives, not layers. A keychain *error* — locked, no secret service running, unreadable entry — falls through to the next step exactly as an absent key does, and so does setting `IRONCLAW_DISABLE_OS_KEYCHAIN`, which skips this step entirely.
  </Step>

  <Step title="Auto-generate">
    Fallback for headless Linux and containers with no reachable keychain. IronClaw generates a fresh key and writes it to the key file above.
  </Step>
</Steps>

An explicitly-set `SECRETS_MASTER_KEY` is validated **before** the cached file is read, so a malformed or empty value fails the boot loudly instead of being silently ignored in favor of a cached key. Non-UTF-8 values are rejected rather than dropped.

Key material — the bytes of the value exactly as supplied — must be at least 32 bytes *and* contain at least 8 distinct byte values. The distinctness check exists because HKDF will happily accept 32 repetitions of `a` as input material; a length-only check would let a placeholder key bootstrap a real store.

<Note>
Deployments that run against PostgreSQL take the master key from a configured environment variable instead — `IRONCLAW_REBORN_SECRET_MASTER_KEY` by default, overridable with `storage.secret_master_key_env`. There is no auto-generation on that path: an unset or unusable key fails the boot rather than silently creating a store no previous secret can be read from.
</Note>

### Per-Secret Encryption

Every secret is encrypted with **[AES-256-GCM](https://en.wikipedia.org/wiki/Galois/Counter_Mode)** under a key derived from the master key plus a random 32-byte per-secret salt ([HKDF-SHA256](https://en.wikipedia.org/wiki/HKDF)), with a fresh 12-byte nonce. Two consequences matter to you:

- Two secrets with the same plaintext produce different ciphertext at rest. Someone who reads the store cannot tell whether two API keys are the same value.
- A single leaked encrypted record is useless on its own. Decrypting it needs the master key, which is never stored inside the database. One caveat: on both the `SECRETS_MASTER_KEY` and auto-generate paths the key is written to the key file under the same runtime root as the store, so for those deployments the encryption is only as strong as the file permissions — copying that directory copies both. Only the keychain path avoids this.

## How a Tool Uses a Secret

The most important property of the system is that **tools never see the raw value of a credential**, even when they make HTTP calls that require one. The secret is attached by the host, in flight, after the tool has handed off the request.

<Steps>
  <Step title="Authorization plans the call">
    Before the tool runs, the authorization layer reads the tool's manifest and plans a set of *obligations* for this specific invocation: which network policy applies, which resource ceilings bind, and — for each credential the tool's manifest declares — a **credential staging obligation**. Which host a staged credential may be attached to is decided later, by that credential's declared audience.
  </Step>

  <Step title="The credential is staged, not handed over">
    Staging leases the secret from the store exactly once and places it where only the *host's* egress service can reach it, bound to this capability and this invocation. A first-party tool consumes the staged copy on its one call; the WASM, MCP, and sandbox lanes may reuse it across the calls of a single invocation, after which it is discarded. It is never passed to the tool, never placed in the tool's environment, and never readable by the sandbox. Production egress accepts only staged credentials; a request that tries to lease a secret directly from the store is refused.
  </Step>

  <Step title="The tool builds an unauthenticated request">
    The tool says, in effect: "POST to `https://gmail.googleapis.com/gmail/v1/users/me/messages/send` with this JSON body." It sets no `Authorization` header — it has nothing to put there.
  </Step>

  <Step title="The host rejects any credential the tool tried to supply itself">
    Before any credential is attached, the egress boundary refuses requests carrying `Authorization`, `Cookie`, `x-api-key`, or similar sensitive headers from the runtime; header values that begin with a credential scheme such as `Bearer ` or `Basic `; query parameters with credential-shaped names such as `api_key` or `access_token`; and `user:pass@` credentials embedded in the URL. This applies to every runtime that sends through the host egress service — WASM, MCP, and first-party alike, including first-party tools that legitimately take model-supplied headers — otherwise the model could smuggle a header of its own choosing to an allowlisted host. (Shell commands running inside a container sandbox reach the network through a separate proxy sidecar that enforces a domain allowlist and private-range denial but does not run these header checks.)
  </Step>

  <Step title="The host scans the request">
    The URL — both raw and percent-decoded — plus the headers and body are run through the leak detector, so a tool trying to smuggle a secret *out* is caught here. This scan runs *before* injection, so a legitimately attached credential can never trip it.
  </Step>

  <Step title="The host injects the staged credential, checks the destination, and sends">
    Per the manifest's `injection` declaration, the host writes the value into a header (with an optional prefix such as `Bearer `), a query parameter, a URL path placeholder, a JSON body pointer, an HTTP Basic credential, or a VAPID authorization — and only into an `https` request (or one to a literal loopback host). Then, before any connection opens, the scheme and host are matched against the tool's declared `network_targets` and credential audiences and private-IP ranges are refused — so a destination the tool did not declare never receives the credential, and every redirect hop is re-checked the same way. The plaintext exists only here, only inside the host process; the request's URL and header values are zeroized when the call ends. Transient copies — the redaction values used to scrub the response, and the HTTP client's own buffers — are freed without wiping, and a value injected into a JSON body is not separately scrubbed.
  </Step>

  <Step title="The response is sanitized before the tool sees it">
    Sensitive response headers are stripped, the injected credential's own value is redacted from the body in case the server echoed it, and the result is leak-scanned. Only then does the response return to the tool — and from the tool to the model.
  </Step>
</Steps>

The tool's view of all this is: "I made a request and got a response." It cannot read the headers that were actually sent. It cannot read its own outbound URL after query-parameter injection. It cannot enumerate the credential store. Those host functions do not exist.

## Why WASM

The "tool never sees the credential" guarantee depends on something the tool cannot bypass. If tools were ordinary binaries the guarantee would be a fiction — a tool could read the secret from disk, or from an environment variable, or from the process that holds it. WASM closes that escape hatch.

A normal compiled program starts with **all** of the host's authority and gives some back. A WASM module starts with **none** and receives exactly what the host hands it. Under wasmtime, a module loaded by IronClaw has:

- No filesystem access
- No network access of its own
- No environment variables
- No ability to spawn processes
- A hard memory cap it cannot exceed, and a fuel budget that terminates it if it loops

Everything beyond that is an explicit host function. The tool interface declares six; the production host grants four, and grants `http-request` only when a network policy has been staged for the call. None of them hands over a secret: `secret-exists` answers yes or no from what was staged for this one invocation, workspace reads and chained tool calls are denied, and nothing lets a module read back the headers the host actually sent. The full grant table is on [WASM Tools](/capabilities/sandboxed-tools#host-functions).

The host starts from a deny-all set and adds capabilities per invocation; a missing grant is a denial, not an omission. Beyond these functions the module is linked against a capability-less WASI context — no preopened directories, environment, stdio, or sockets — so that is the entire surface area.

The practical implication: a malicious or compromised WASM tool cannot read your SSH keys, reach your `.env`, install anything, or persist state outside what its manifest declared. What it *can* still do is bounded by what you granted — and that grant is not nothing. A compromised tool can make authenticated requests to its declared hosts with data of its own choosing. The sandbox bounds the blast radius; it does not make an over-granted tool harmless. Approve `network_targets` and credentials narrowly.

For fuel, memory, and manifest details, see [WASM Tools](/capabilities/sandboxed-tools).

## The Leak Detector

Credential injection keeps secrets out of the tool. The leak detector is the pattern-matching layer that catches secrets moving where they shouldn't — in either direction.

Even though a tool never saw the credential it sent, the **server it called** might send it back:

- An API returns `unauthorized: token sk-abc123… is invalid`
- A debug endpoint reflects request headers into the response body
- A misconfigured upstream pastes the credential into a downstream payload

If that reaches the model verbatim, the secret is in the model's context, and from there it can flow into the next tool call, into a saved memory, or onto your screen.

The detector is also the second line of defense in the other direction: a compromised tool that tries to smuggle a secret *out* in a URL, header, or body is caught before the request leaves.

### Pattern Catalog

The detector ships 23 regex patterns:

| Category | Patterns |
|----------|----------|
| LLM provider keys | OpenAI (`sk-…`, `sk-proj-…`), Anthropic API (`sk-ant-api…`), Anthropic OAuth (`sk-ant-oat##-…`), OpenRouter (`sk-or-v1-…`), Groq (`gsk_…`), NEAR AI session (`sess_…`) |
| Cloud credentials | AWS access key ID (`AKIA…`), Google API key (`AIza…`) |
| Developer platforms | GitHub classic tokens (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`) and fine-grained PATs (`github_pat_…`) |
| Payment / messaging | Stripe (`sk_live_…`, `sk_test_…`), Slack (`xoxb-`, `xoxp-`, …), Twilio API key (`SK<32 hex>`), SendGrid (`SG.<…>.<…>`), Telegram bot token (`<digits>:AA…`) |
| Private keys | PEM RSA / PKCS#8 / encrypted, OpenSSH / EC / DSA, and OpenPGP private-key armor — matched as complete blocks so a partial redaction can't leave key material behind |
| Generic structures | Bare JWTs (three-segment, header decoded and validated), `Bearer <token>`, `Authorization:` headers, 64-character hex blobs |
| Sandbox placeholders | `icsbx_…` credential placeholders — inert on their own, but treated like a real secret so one can never cross into model output or logs |

Each pattern carries a severity and an action:

| Action | Effect | Used for |
|--------|--------|----------|
| **Block** | The content is rejected; the call fails rather than passing the match through. | Critical and high-severity credentials — provider keys, cloud keys, private keys, sandbox placeholders. |
| **Redact** | The matched span is replaced before the content moves on. | Shapes that are often legitimate in context — bearer tokens, `Authorization` headers, bare JWTs. |
| **Warn** | Logged at debug level; the content passes this boundary. (Compaction and trace contribution redact these matches too.) | Ambiguous shapes such as 64-character hex, which is as often a hash as a secret. |

### Where the Scan Runs

The detector is not one gate; it is installed at each boundary where untrusted content changes hands.

| Boundary | What it protects |
|----------|------------------|
| **Outbound HTTP request** | The URL (raw and percent-decoded), headers, and body of every runtime HTTP call, before the real credential is attached. Catches a tool trying to smuggle a secret out. |
| **Inbound HTTP response** | The response body from an external API, before the calling tool's code sees it. Sensitive response headers are stripped and the injected credential's own value is redacted alongside the pattern scan. |
| **Command output** | Shell and process output, before it becomes a model-visible preview or a saved artifact. A blocking match replaces the whole output rather than redacting part of it. |
| **Model-visible error detail** | Failure text from tools and providers, which is redacted in place — the descriptive cause survives with only secret values masked — and fenced as untrusted content if injection patterns remain. |
| **Context compaction** | Conversation history on its way through summarization, so a secret can't be laundered into a compacted summary that outlives the turn it appeared in. |
| **Trace contribution** | Traces before they leave the machine, so a shared trace can't carry a credential with it. |
| **Operator logs** | A diagnostic surface that would otherwise sit outside every other scan. (LLM recordings are redacted by a separate header/field allowlist, not this detector.) |

<Note>
**The scans stack.** A WASM tool calling an external API has its *outbound request* scanned before injection, and its *response* scanned at the host boundary before the sandbox sees it. A first-party tool shelling out has its command output scanned again on the way to the model.
</Note>

<Warning>
There is no universal "scan everything a tool returns" gate today. The host supports one as an obligation, but production authorization never attaches it — coverage comes from the specific boundaries in the table above. A tool that fabricates a secret-shaped string in its own JSON output, without touching HTTP, the shell, or an error path, is not scanned on the way to the model. Shell output from a command run inside a Docker user-sandbox container is not scanned on the process path either. These are real gaps, not omissions from these docs.
</Warning>

## Worked Example: Sending an Email

What happens when you ask IronClaw to send a Gmail message.

<Steps>
  <Step title="You say: 'Email Alice with the meeting notes'">
    The model selects `gmail.send_message` and calls it with `{ to: "alice@example.com", body: "…" }`.
  </Step>

  <Step title="Authorization gates the call">
    The manifest declares `default_permission = "ask"` for this tool, and effects including `external_write`. That makes the call approval-eligible: it pauses for you if global auto-approve is off or you have set this tool to ask each time; on a default install, where auto-approve is on, it proceeds. It also declares `origin_gate_matrix` with `automation = "forbidden"`, so routine/heartbeat automation cannot invoke it at all; a run started by a scheduled trigger is an agent turn and meets the same `loop_run` gate as this one.
  </Step>

  <Step title="Your OAuth token is staged — not handed over">
    Authorization emits a one-shot credential obligation for the `gmail_account` handle, whose declared audience is `gmail.googleapis.com`. The secret is placed where the host's egress service can consume it exactly once, for exactly this call.
  </Step>

  <Step title="The tool builds an unauthenticated request">
    The tool constructs a POST with no `Authorization` header. It cannot read your OAuth token: the token is encrypted at rest and only the host's egress boundary can consume the staged copy. (Gmail ships as a first-party tool rather than a WASM module, so here the guarantee rests on that egress chokepoint rather than on the sandbox — the same rules apply to every runtime.)
  </Step>

  <Step title="The host validates, scans, then injects">
    The URL, headers, and body are leak-scanned. The host takes the staged token and writes `Authorization: Bearer …` onto the outbound request, then confirms `gmail.googleapis.com` matches the tool's declared `network_targets` before opening the connection.
  </Step>

  <Step title="Gmail responds, and the response is sanitized">
    Gmail returns `{ id: "abc123", threadId: "…" }`. Sensitive headers are stripped, the token's own value is redacted in case it was echoed, and the body is leak-scanned. Nothing matches, so the response passes to the tool.
  </Step>

  <Step title="The model summarizes for you">
    The model produces "Sent your message to Alice (id abc123)". The OAuth token never entered the model's context.
  </Step>
</Steps>

At no point did your OAuth token enter the model's context, the tool's memory, a log line, or the event stream you can see.

## What This Doesn't Defend Against

No security model is total. To set expectations clearly:

<AccordionGroup>
  <Accordion title="A compromised host process" icon="triangle-alert">
    The host holds the master key in memory and can decrypt any secret. If an attacker gets root on the machine running IronClaw, the secret store is exposed. Defense at this layer is your operating system's job. Run IronClaw on a machine you trust.
  </Accordion>

  <Accordion title="An over-granted manifest" icon="file-warning">
    A tool can only do what its manifest declares, but you approve that manifest at install time. A tool declaring broad host patterns and a sensitive credential is a tool that can use that credential against those hosts. Read `network_targets` and `credentials` before installing an extension from an untrusted source.
  </Accordion>

  <Accordion title="An upstream API that legitimately needs the secret" icon="link">
    Credential injection puts your token in a request to an API you chose to trust. If that API is itself compromised or malicious, it has your token. IronClaw enforces the boundary; the trust decision is yours.
  </Accordion>

  <Accordion title="Novel secret shapes the detector doesn't know" icon="shield-question">
    The leak detector covers common credential formats. A custom internal token with no recognizable shape will not match. If you operate such a service, its token is only protected by the structural layers — injection at the host boundary and the sandbox — not by pattern matching.
  </Accordion>

  <Accordion title="Tool output that never crosses a scanned boundary" icon="scan-line">
    As noted above, there is no blanket scan on every tool result. A tool that emits a secret-shaped string it constructed itself, without an HTTP call, a shell command, or an error path, reaches the model unscanned.
  </Accordion>
</AccordionGroup>

The system is designed so that the most likely failure modes cannot happen by construction: the model leaking a secret it was helpfully shown, or a tool reading credentials it was not granted. The remaining risks are the ones a human is in the loop to evaluate.
