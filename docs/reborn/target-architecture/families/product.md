# Family: `crates/product/` — first-party userland above the kernel

**Layer(s):** `products` (unchanged — every crate in this family is `products` today and stays `products`) · **Crates (target):** 5 — `ironclaw_product` (narrowed) · `ironclaw_operator` (narrowed, contracts flip) · `ironclaw_openai_compat` (renamed from `ironclaw_reborn_openai_compat`) · `ironclaw_webui` · `ironclaw_host_ingress` · **Security posture:** holds no standing authority of its own — every privileged effect it triggers crosses a kernel port it does not define. Its own trust jobs are narrow and named: host authentication at the HTTP edge (`webui`, T1), admission/binding/idempotency at the product boundary (`product`, T3), and delivery *semantics* that hand off to `outbound`'s sealed at-most-once reservation rather than owning it (T8).

Source authority: `docs/reborn/target-architecture/PROPOSAL.md` §5, §6.9, §7 (T1/T3/T8), §8, §9 rows 59–63, §10.4, §12.1/§12.10. Live-code citations below were re-verified against the worktree this session (`dde662d5a` baseline); re-check file:line before acting on them.

## Identity — what this family IS

`product/` is the supported first-party experience: the one place that turns raw, already-verified channel/HTTP traffic into admitted, idempotent, durably-bound turns, and turns kernel/domain state back into redacted, product-safe views and deliveries. Concretely today it is `ironclaw_product`'s `RebornServices` implementing `ProductSurface` (`workflow.rs:202`, `DefaultProductSurface`), plus four crates that sit around it: `ironclaw_operator` (the deployment-operator control plane — LLM admin, logs, service lifecycle), `ironclaw_openai_compat` (an OpenAI-shaped protocol adapter over the same surface), `ironclaw_webui` (the browser-facing HTTP gateway, host authentication, and the embedded SPA), and `ironclaw_host_ingress` (the Axum route-mount vocabulary that keeps `axum` out of contracts). Combined current mass: `ironclaw_product` 51,619 src + 36,789 test lines; `ironclaw_operator` 9,669 src; `ironclaw_openai_compat` 7,039 src + 7,895 test; `ironclaw_webui` 23,440 src + 16,885 test (+ a ~4.8 MB Vite SPA bundle embedded via `build.rs`, 295 ln); `ironclaw_host_ingress` 108 src lines. `ironclaw_product` alone is a fifth of the family's src mass and stays that way — §6.9.1 narrows what it owns, not how much of the family's real work it does.

The family's job is to be the *stable* thing three different front doors (browser SPA, OpenAI-compatible API clients, and — one layer down, in `extensions/packages/*` — channel adapters) all converge on, so none of them reimplements binding resolution, idempotency, command grammar, or delivery policy. `ironclaw_product`'s own module doc says this almost verbatim: it "owns the product action orchestration so that adapters (Web, API, CLI, Telegram, etc.) do not each reimplement binding resolution, message staging, idempotency, busy/deferred handling, gate routing, mission routing, and redacted acknowledgements" (`crates/ironclaw_product/src/lib.rs:1-7`). `operator` and `openai_compat`/`webui` are asymmetric around that center: operator is control-plane, not conversation-plane (it is a *deployment*-operator surface, not a channel), while openai_compat/webui are two protocol skins over the same conversational core.

A worked illustration of the discipline this buys (PROPOSAL §10.4, "archive conversation"): adding a new product command touches at most three crates — `product_contracts` only if a genuinely new wire DTO is unavoidable (the descriptor *types* already exist there), `ironclaw_product` for the command-descriptor constant plus the durable mutation call into `ironclaw_threads` (the record authority), and `ironclaw_webui` for one descriptor row + handler + SPA affordance. Composition gets no new handle (the generic `invoke` surface already carries it), kernel gets no new authority kind, and `host_api` gets nothing neutral to add. That three-crate blast radius — never four, never touching kernel or app — is the family's reason to exist.

## What makes it distinct

**vs `kernel/` — product asks, kernel decides.** Every capability invocation, authorization, and lease in this codebase is a kernel-family act; product never authorizes, never mints an `Authorized` witness, never holds ambient secrets or network handles, and never talks to `host_runtime`/`dispatcher`/`mcp`/`wasm`/`scripts`/`network` directly. `ironclaw_product`'s own `CLAUDE.md` states this as a boundary rule — "Must NOT depend on: `ironclaw_dispatcher`, `ironclaw_extensions`, `ironclaw_host_runtime`, `ironclaw_mcp`, `ironclaw_wasm`, `ironclaw_scripts`, `ironclaw_network`, `ironclaw_engine`, `ironclaw_gateway`" (`crates/ironclaw_product/CLAUDE.md:45-47`) — and PROPOSAL §8.2 retains it verbatim for the target ("product still ✗ `host_runtime`/dispatch/lanes — rule retained"). Where product needs a kernel decision it goes through a *read-model or resolution port* it doesn't own the implementation of: `ApprovalInteractionService`/`AuthInteractionService` render redacted click-approval/click-auth views and forward decisions through `ApprovalResolutionPort`/`TurnCoordinator` — they never execute a tool or mutate an approval store directly (`crates/ironclaw_product/CLAUDE.md:62-72`). Kernel mediates; product narrates and asks.

**vs `extensions/` — product is not an extension.** Invariant 3 (PROPOSAL §3) and the README's family table both say this outright: product is "first-party userland above the kernel and is not an extension." It has no manifest, no installation lifecycle, no runtime binding, no `ChannelAdapter` implementation. Conversation UX — binding, idempotency, command grammar, delivery *semantics* — is product's job; extension *management* UX (catalog browsing, install/remove, channel config, pairing workflows) is a **different family's** crate, the new `extensions/ironclaw_extension_manager` (products-*layer*, extensions-*family* — a clean example of family ≠ layer, PROPOSAL §6.8.3). Today the two are entangled in both directions and the entanglement is exactly backwards: `ironclaw_extension_host` sits *above* `ironclaw_product` (a normal dependency, 106 references, because the ports it implements — delivery resolver, reply-context source, admission, pairing sources, preference codec — are defined *in* product), and `ironclaw_product` itself depends on `ironclaw_extensions` (`crates/ironclaw_product/Cargo.toml:37`, used by `adapter_registry.rs:14-20` to parse `ironclaw.product_adapter/v1` manifest sections) even though `ironclaw_product/CLAUDE.md:45-46` lists `ironclaw_extensions` in its own "must not depend on" list — a live guidance-vs-code contradiction the target resolves by relocating the manifest-vocabulary need into `extension_contracts` and inverting the port-ownership so `extension_host`/`extension_manager` depend on `product_contracts`, not `product`.

**vs `contracts/` — product implements `ProductSurface`, it does not define it.** Today the trait, its DTOs, and its command/view/capability descriptor *types* live inside `ironclaw_host_api::product_surface` and get re-exported wholesale through `ironclaw_product`'s ~230-symbol facade (`crates/ironclaw_product/src/lib.rs:62-402`, the bulk of it one `pub use reborn_services::{...}` block spanning lines 254–393). That location is precisely what forces `extension_host`, `operator`, and `telegram_extension` to sit *above* product for their port needs. `ironclaw_product_contracts` (PROPOSAL §6.1.3) carves the trait, the wire DTOs (including the 43-variant `AppEvent` enum moving out of `common::event`), the descriptor *types* (not product's frozen 27/33/18 concrete constants — those stay), and the operator/delivery/lifecycle *ports* out into a neutral home. After the split, product is one of several implementors that happens to hold the canonical implementation — the frozen-surface ratchet (`host_product_surface_method_set_is_frozen`) still pins *its* method set, but the trait itself belongs to contracts.

**vs `app/` — product owns a domain, `app` assembles it.** Composition constructs `ironclaw_product`'s dependencies (approvals, authorization, turns, threads, …) and hands the finished `Arc<dyn ProductSurface>` to `webui`/`openai_compat`; it never itself implements `ProductSurface`, never itself resolves a binding, never itself decides a command grammar. Conversely product never wires anything — it has no factory functions that construct other crates' concrete stores, no profile/deployment-mode branching. The one place this line blurs today is composition's `runtime/local_dev/**` tree (see `app.md`), which currently *is* the production capability/delivery/approval/skill path despite living in the app-family crate — that mass sheds to product/kernel/domains owners in the target, not the other way around.

## What belongs here / What must never be here

**Belongs:** the `ProductSurface` implementation and its admission/binding/idempotency machinery; command grammar (product commands are explicitly *not* turns — `crates/ironclaw_product/CLAUDE.md:54-60`); delivery **semantics** (retry policy, reply-context resolution, coordinating *when* and *through which resolved target* to speak — never the transport call itself, which lives in an extension package); the deployment-operator control plane (LLM provider admin, operator logs, OS service lifecycle — a *different* "operator" than the extension-management UX, see below); the two HTTP-facing protocol adapters (`webui`'s SPA+API, `openai_compat`'s OpenAI-shaped surface); and the thin Axum-carrier vocabulary (`host_ingress`) that lets `webui`/`operator` hand composition a prebuilt router without contracts ever importing `axum`.

**Must never be here:** authority decisions of any kind (kernel's job); lane mechanics or vendor *protocol* behavior beyond the two license exceptions the specificity scanner already carves out for this family — `operator`'s LLM-vendor admin (NEAR-AI/Codex login flows, `nearai_mcp.rs`) and `webui::auth`'s OAuth login providers (`GoogleProvider`/`GitHubProvider`) — per PROPOSAL §8.1 rule 4; and assembly/wiring, which is `app`'s job exclusively. Raw secrets, raw host paths, backend error strings, or unredacted user content must never cross a product-family error, event, snapshot, or log boundary — `ironclaw_product/CLAUDE.md` states this as a hard rule for approval/auth interaction DTOs and it holds family-wide.

## Dependency direction

Product still holds the retained "forbidden" list from `kernel-boundary.md`/`CLAUDE.md`: no `host_runtime`, no `dispatcher`, no lane crates (`mcp`, `wasm`, `scripts`, `network`), no `engine`/`gateway` (both nonexistent already). The target adds one enforcement gap-fix: `ironclaw_extensions` joins that forbidden list *mechanically*, not just in prose, closing the `adapter_registry.rs` contradiction above.

`webui` and `openai_compat` depend on `product_contracts` (plus `extension_contracts` where channel DTOs are shared) instead of `ironclaw_product` in the target — `ironclaw_product` itself becomes the *only* crate in the family that still holds the full "product mass" (the `reborn_services` orchestration, the ledger, the binding/conversation logic). This is the direct fix for today's inversion: `extension_host → product` (106 refs) and `operator → product` (4 confirmed import sites, below) both become `→ product_contracts`, and the family's internal shape changes from "one crate everyone imports for both vocabulary and behavior" to "one crate that owns behavior, one crate that owns vocabulary, four crates that consume the vocabulary."

Sibling edges within the family stay legal under §8.2's "products → products: siblings" rule and are used today: `webui` depends on `ironclaw_reborn_openai_compat` (`crates/ironclaw_webui/Cargo.toml:43`) specifically to stamp an `OpenAiCompatActorScope` onto verified callers for protected OpenAI-compatible route mounts — this edge is unaffected by the restructure. `host_ingress` sits at the bottom of the family (deps: `axum`, `host_api` only) and is depended on by `webui`, and — once its narrowing lands — `operator`, which today builds its own parallel `OperatorPublicRouteMount`/`OperatorProtectedRouteMount` carrier types (`crates/ironclaw_operator/src/route_mounts.rs:1-37`) instead of reusing `host_ingress`'s identically-shaped `PublicRouteMount`/`ProtectedRouteMount`. `webui` is the one crate in the family meant to own `axum` as a *listener*-binding concern (§8.1 rule 5); `operator`'s current direct `axum = "0.8"` dependency (`crates/ironclaw_operator/Cargo.toml:18`) for router construction is exactly the kind of edge the `host_ingress` carrier move is meant to retire.

## Security & authority role

**T1 — external → authenticated request (`webui`).** The listener + fixed middleware order (ws-origin → per-route body limit → bearer/session/OIDC auth → rate limit → handler, `crates/ironclaw_webui/CLAUDE.md:53-55`) is entirely this crate's job; `EnvBearerAuthenticator`, `SessionAuthenticator`, and `OidcAuthenticator` (`crates/ironclaw_webui/src/{lib.rs,session.rs,oidc.rs}`) are the three `WebuiAuthenticator` impls that decide who the caller is. The bearer-evidence mint is the concrete security-boundary change PROPOSAL §7/§12.1(a) calls out: the eight `mark_*_verified[_for_tenant]` constructors are *defined* in `crates/ironclaw_host_api/src/product_adapter/auth.rs:366-464`, each gated `#[cfg(feature = "host-auth-mint")]` at the definition site; `ironclaw_product`'s `host-auth-mint` feature (`Cargo.toml:21`, `= ["ironclaw_host_api/host-auth-mint", "ironclaw_turns/host-auth-mint"]`) is a pass-through that unlocks them, and `ironclaw_webui` pulls that feature on (`Cargo.toml:37`) purely to call `mark_bearer_token_verified_for_tenant` at its one real call site (`crates/ironclaw_webui/src/webui_serve.rs:60,787`). `ironclaw_webui/CLAUDE.md:35` already claims "no direct `ironclaw_product` edge (reach it through composition's facade)" — a guidance line the Cargo manifest already contradicts. The target (§6.9.4, §11.2.5) deletes the `host-auth-mint` feature-flag indirection entirely: the mint functions stay in `host_api`, always compiled, but visibility-sealed to the authenticator/verifier call sites (mirroring the existing `authorized-seal` ratchet), and a pinned test asserts the feature name is gone workspace-wide. Public webhook routes (T1′) skip host auth by declared `ListenerClass::PublicWebhook` policy and flow to T2 in the extensions family instead — product never verifies a webhook signature.

**T3 — product request → durable admitted work.** `ironclaw_product` resolves binding, checks replay/idempotency (`IdempotencyLedger`), admits the command (`ProductCommandAdmissionService`), and only then hands off to `TurnCoordinator` (kernel/`turns`) to persist under the one-active-run-per-thread lock. This is the crate's one real "decision," and it is a *durability* decision, not an authority one — it decides whether a request is a duplicate or in-flight, never whether it is allowed. The one host-minted inbound exception (trusted-trigger submission) is explicitly *not* product's — it stays sealed in `triggers`/`conversations`.

**T8 — decision to speak → external delivery.** `DeliveryCoordinator` (`crates/ironclaw_product/src/delivery_coordinator.rs:1-709`, 10 `DeliveryIntent` variants) owns delivery *semantics* — which target, what retry policy, what reply-context — but the at-most-once guarantee itself (the sealed `Prepared→Sending` CAS reservation) lives in `outbound` (domains family), not here; product calls into it and then calls `ChannelAdapter::deliver` on the resolved package. `DeliveryCoordinator` is constructed at exactly one production site (composition `factory.rs:5534`) and driven only from `extension_host`'s `channel_host.rs` today — the target inverts that to `extension_host` driving it through a `product_contracts` port instead of importing `ironclaw_product` directly.

**§12.1(b) — the secrets-tightening constraint.** `ironclaw_operator` holds a *normal* dependency on `ironclaw_secrets` today (`Cargo.toml:28`, confirmed used beyond tests); `ironclaw_webui`'s only `ironclaw_secrets` use is a **dev-dependency** consumed by two test modules (`product_auth/oauth_start_tests.rs:21`, `product_auth/mod.rs:1730`) — so the live risk is narrower than "both crates reach the store in production," but operator's edge is real and the target constraint (§6.2.2) removes it: operator's secret needs route through `product_contracts` ports implemented by composition-wired services instead of `ironclaw_secrets::SecretStorePort` directly.

## Family AGENTS.md obligations

A single `AGENTS.md` at `crates/product/` states, once, for the whole family: the frozen-surface rule (`host_product_surface_method_set_is_frozen` — a method added to `ProductSurface` is a breaking-surface change, not a routine edit); "transports consume contracts, not owners" (`webui`/`openai_compat` import `product_contracts`, never `ironclaw_product` directly, once the split lands); the trusted-ingress prohibition (no product-family crate mints trusted inbound evidence — that's `extension_contracts`'/`host_api`'s job, sealed to verifier/authenticator call sites only); the family's narrow vendor exception scope (LLM-vendor admin in `operator`, OAuth login providers in `webui::auth` — nowhere else); and "`webui` owns `axum`" as the one framework-dependency rule specific to this family.

Crate-local guidance keeps the existing `AGENTS.md`/`CLAUDE.md` convention. `ironclaw_operator` is one of the **six crates PROPOSAL §11.4 names as currently guidance-less** (alongside `extension_host`, `attachments`, `traces`, `mem0`, `prompt_envelope`) and gets both files for the first time as part of its move — the audit's clearest correlation (guidance presence ↔ discipline) applies directly here, since operator is also the crate with the least-enforced boundary today (zero dedicated architecture-test coverage beyond the workspace-wide matrix).
