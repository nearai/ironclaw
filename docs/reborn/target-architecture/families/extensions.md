# Family: `crates/extensions/` — everything "installable package"

**Layer(s):** mixed by design — `substrates` (`ironclaw_extensions`), `loops` (`ironclaw_extension_host`, `packages/first_party`), `products` (`ironclaw_extension_manager`, `packages/slack`, `packages/telegram`) · **Crates (target):** 6 — `ironclaw_extensions` (re-layered), `ironclaw_extension_host` (narrowed, re-layered), `ironclaw_extension_manager` (NEW by split), `ironclaw_first_party_extensions` (widened), `ironclaw_slack_extension`, `ironclaw_telegram_extension` (widened, absorbs `ironclaw_telegram_v2_adapter`) · **Security posture:** the host↔extension trust membrane, physically colocated with everything downstream of it — the generic ingress verifier is the only code in the workspace permitted to mint sealed verified-inbound evidence (T2), concrete packages parse and render but can never construct trust, and only `ironclaw_cli` may link a concrete package crate into the binary (mechanically enforced today).

## Identity — what this family IS

`crates/extensions/` is every "installable package" concern except the neutral vocabulary those concerns share. `docs/reborn/extension-runtime/overview.md`'s landed model is the premise this family physicalizes: an extension is the *only* installable product object, its surfaces are `tool`/`channel`/`auth` (trigger/file reserved), `VendorId` is a credential authority namespace that is never product identity, and at most one channel surface exists per extension. That model names four host pipelines implemented exactly once — dispatcher (tool), ingress router (inbound), delivery coordinator (outbound), auth engine (recipes only) — and this family owns the generic implementations of the first two plus the product-facing orchestration around all four. PROPOSAL §6.8's family role states the split this document follows: "the four separated extension responsibilities, physically colocated: neutral surface vocabulary lives in `contracts/` (§6.1.2); this family holds **registry/records**, **generic hosting**, **product-side management**, and **concrete packages**." The Discord worked example (PROPOSAL §10.1–§10.3) is the concrete proof the split holds: adding a full channel — inbound parsing, delivery, and one model-callable tool — touches exactly one new package directory (`extensions/packages/discord/`, `manifest.toml` + `impl ChannelAdapter`, deps = `extension_contracts` only) plus one binding-table line in `app/ironclaw_cli`; `ironclaw_extension_host` is untouched because "verification is recipe *data*; router/verifier are generic — proven by Slack's 15-line TOML seam" (`crates/ironclaw_first_party_extensions/assets/slack/manifest.toml:201-220`, verified this session), and `ironclaw_product`/kernel/substrates are untouched because binding, admission, delivery semantics, and egress policy are all channel-agnostic by construction. That is what "everything installable-package" buys: a genuinely new vendor is a package-directory diff, never a generic-crate diff.

## What makes it distinct

- **The four separated responsibilities, and where each actually lives.** *Vocabulary* — `ChannelAdapter`/`ToolAdapter`, manifest-surface descriptors, auth recipes, `InstallationState`, and the sealed verified-inbound evidence constructors — is explicitly **not** in this family; it lives in `contracts/ironclaw_extension_contracts` precisely so lanes, hosts, packages, product, and the manager can share one vocabulary without any of them importing a registry (§6.1.2). *Registry/records* is `ironclaw_extensions` alone: manifest schemas plus the durable installation/membership/credential-binding store. *Generic hosting* is `ironclaw_extension_host` alone: lifecycle writer, loaders, binding, activation, the ingress verifier, egress transports. *Product-side management* is the new `ironclaw_extension_manager`: catalog UX, lifecycle commands, channel-config and pairing product services, credential views. *Concrete package behavior* is `packages/*`: parsing, rendering, vendor API calls, recipe data. No other family may hold a fifth copy of any of these — `product/ironclaw_product` owns conversation UX, never extension UX.
- **vs `product/`** — extension **management** UX vs conversation UX. Today `composition` already assembles a second `ProductSurface` implementation, `SharedCommandSurface` (`crates/ironclaw_extension_host/src/channel_host.rs:282`, verified `impl ironclaw_host_api::ProductSurface for SharedCommandSurface`), for exactly this reason: "install/configure/pair an extension" and "have a conversation" are different surfaces serving different intents, and `ironclaw_extension_manager` is that existing seam made physical, not a new one invented by this proposal.
- **vs `lanes/`** — package vs mechanism, two orthogonal axes. A package (`extensions/packages/github/`) is a distribution/vendor/configuration unit: what ships, what it's allowed to touch, how it's configured. A lane (`lanes/ironclaw_wasm`, `.../ironclaw_mcp`, `.../ironclaw_sandbox`) is an execution mechanism: how already-authorized code runs. The GitHub tool's WASM binary is built from `packages/first_party/assets/github/wasm-src/` and *runs* in the `wasm` lane; the package never depends on the lane crate, and the lane never depends on the package crate — the manifest's `runtime.kind = "wasm"` field is the only thing that connects them.
- **"Runtime kind is loading, never taxonomy"** (invariant #9, PROPOSAL §3). The three loaders — first-party native, WASM, MCP — all produce the identical `ExtensionBindings { tools, channel }` shape from `ExtensionEntrypoint::bind`; nothing in `ironclaw_extensions`' schema, `ironclaw_extension_host`'s activation path, or `ironclaw_extension_manager`'s catalog branches on which loader built a given extension. A package choosing WASM over native is an implementation decision recorded in one manifest field, not a different product category.

## What belongs here / What must never be here

**Belongs:** manifest schemas and installation/membership records; the generic lifecycle/binding/activation/removal state machine; the generic ingress verifier and egress transports; product-facing catalog, lifecycle-command, channel-config, and pairing services; concrete per-vendor parsing, rendering, and vendor API calls. **Must never be here:** vocabulary/port trait definitions (→ `contracts/ironclaw_extension_contracts`); a second dispatcher, ingress router, delivery coordinator, or auth engine per package (the four host pipelines are implemented exactly once, generically); vendor names outside `packages/` — the specificity scanner's rule-4 allowlist (§8.1) restricts vendor names to exactly `packages/*`, `llm` providers, `operator` (LLM-vendor admin), `webui::auth` login providers, and recipes-as-data, and every crate in this family except the packages themselves is scanned against it. **The package-directory self-containment rule** (§5's closing legend): a package directory under `extensions/packages/` is the unit of self-containment — manifest, assets, prompts, schemas, code, and `wasm-src` travel together, not scattered across a code crate here and an asset tree elsewhere (today's Slack split, code in `ironclaw_slack_extension` and assets in `ironclaw_first_party_extensions/assets/slack/`, is exactly the arrangement this rule ends). **The package⇒crate rule** (§5, verbatim): "a package gets its own crate iff it has a channel adapter (binary-only linking, enforced by `concrete_extension_crates_link_only_from_the_binary_and_tests`) or a heavy/isolated native dependency; pure-WASM/MCP/recipe packages are directories with assets only; shared native tool executors live as modules in `ironclaw_first_party_extensions`."

## Dependency direction

`ironclaw_extensions` depends only on `substrate/` (`filesystem`) and `contracts/` (`host_api`, `extension_contracts`, trust vocabulary via `host_api`) — verified clean today (`Cargo.toml`: `ironclaw_filesystem`, `ironclaw_host_api`, `ironclaw_trust` and nothing else). `ironclaw_extension_host` depends on `kernel/` siblings it hosts activity for (`capabilities`, `auth`, `conversations`, `processes`, `resources`, `secrets`, `trust`, `turns`), on `ironclaw_extensions` and `ironclaw_loop_host`, and on `contracts/` — and **must not depend on `product`**. §8.2's forbidden-edge matrix states this as the family's one restored invariant: `extensions/ironclaw_extension_host` may reach `allowed` substrates, `allowed` kernel, `siblings/loop`, but "**✗ product**." `ironclaw_extension_manager` inverts today's shape: it depends on `product_contracts` and `extension_contracts`, plus `ironclaw_extension_host` and `ironclaw_extensions` themselves (calling their authority, never reimplementing it) — never the reverse. Every `packages/*` crate depends on `extension_contracts` only (the model Slack already is); `packages/first_party` additionally depends on the domains its bundled tools need by charter (`auth` for gsuite, `traces`/`memory`/`skills`/`triggers` for the absorbed builtin tools).

**The §12.1(c) ordering constraint — the sharpest edge in the whole restructure.** `ironclaw_extension_host` sits *above* `ironclaw_product` today (a normal dependency, 106 references, verified `Cargo.toml`: `ironclaw_product = { path = "../ironclaw_product", features = ["host-auth-mint"] }`), because the ports it implements — delivery resolver, reply-context source, admission source, pairing sources, preference codec — are *defined* in `ironclaw_product`, and its ingress calls product's sealed host-auth mint directly (`extension_ingress.rs:88,94`). The target re-layers `extension_host` from `products` to `loops`, which is below `products` in the matrix — but re-layering *first* would simply fail to compile, because the crate's product dependency would then point upward across the ladder. PROPOSAL §12.1 states the constraint exactly: "(c) Re-layering `extension_host` below product removes its ability to call product's minting/admission directly — the port inversions must land *before* the layer flip or the crate won't compile; that ordering constraint is the sharpest edge in the whole restructure." Concretely: the five port sets must land in `contracts/product_contracts` and `contracts/extension_contracts` (§6.1.2, §6.1.3) and `ironclaw_extension_host` must be repointed to implement the contracts-tier ports instead of the concrete `ironclaw_product` types, *before* its `[package.metadata.ironclaw] layer` line changes from `"products"` to `"loops"` — reversing that order is not a style preference, it is a compilation-order dependency this document flags for whoever sequences the work.

## Security & authority role

**T2 — raw webhook → verified inbound** (PROPOSAL §7) is this family's signature trust transition, and it happens entirely inside `ironclaw_extension_host`: manifest-recipe signature verification (HMAC/shared-secret; replay window; constant-time compare), body bounds, then — and only then — the sealed **verified-inbound evidence** is minted from the `extension_contracts` sealed constructor; "the vendor adapter *never* constructs trust." The `ChannelAdapter::inbound` call that follows (in a package crate) is pure parsing into `NormalizedInboundMessage` — "a malicious adapter can lie about content but cannot forge verification or scope." Slack's manifest is the concrete proof this is recipe *data*, not code, verified this session at `crates/ironclaw_first_party_extensions/assets/slack/manifest.toml:207-220`:

```toml
[channel.ingress.verification]
kind = "hmac_sha256"
secret_handle = "slack_signing_secret"
signature_header = "X-Slack-Signature"
signature_prefix = "v0="
signature_encoding = "hex"
timestamp_header = "X-Slack-Request-Timestamp"
max_age_seconds = 300
signed_payload = [
  { literal = "v0:" },
  { header = "X-Slack-Request-Timestamp" },
  { literal = ":" },
  { body = true },
]
```

The generic verifier (`ironclaw_extension_host/src/ingress/verifier.rs`, 1,058 lines) executes this recipe for every vendor identically; nothing in `ironclaw_slack_extension` or `ironclaw_telegram_extension` performs or can perform signature verification. Downstream, **T8 — decision to speak → external delivery** closes the loop from this family's side: `domains/ironclaw_outbound` mints a sealed access grant, `product`'s `DeliveryCoordinator` drives semantics, and the package's `ChannelAdapter::deliver` renders and calls the vendor only through mediated egress with host-injected credentials — the adapter never holds a raw bot token. **A named, tracked tightening** (PROPOSAL §12.1(a)): today two feature-gated evidence-mint families exist in parallel — `host_api::product_adapter::auth::mark_bearer_token_verified` (bearer/session, `host-auth-mint` feature) and `product::auth::mark_request_signature_verified`/`mark_shared_secret_header_verified` (the ones `extension_ingress.rs:88,94` calls, and the reason `extension_host` needs the `host-auth-mint` feature on its `ironclaw_product` dependency at all today). The target consolidates channel/webhook evidence minting into `extension_contracts`' sealed constructor, called only by the generic verifier — a security-boundary tightening, not a behavior change, and one whose prerequisite is that the existing ingress/auth contract tests move with the constructors and a refute-style test proves adapters and products cannot mint (§12.1(a)).

The charter itself is corrected in the same move: it stops claiming the whole crate is "side-effect free" — `installations.rs` is a genuine persistence adapter with boot-repair passes — while the registry/manifest half keeps that claim, since it is actually pure.
- **Owns:** manifest schemas (v3 wire / v2 internal / resolved+digest, with the reparse gate keeping production off TOML re-parsing); the in-memory registry/catalog snapshot; the durable installation/membership/credential-binding records and their CAS migrations. `LifecyclePublicState`/`InstallationState` themselves are **not** owned here — they live in `contracts/ironclaw_extension_contracts` (today `host_api::state`) — this crate stores and CAS-updates records shaped by that contract vocabulary, it does not define the vocabulary.

- **Public contracts & ports:** none defined here — this crate consumes `extension_contracts` vocabulary and exposes registry/store operations, it does not define ports for others to implement.
- **Security & authority role:** "the only installation-lifecycle authority" per its own contract (caller membership) — a domain-record authority, not a mediation stage; it never decides whether an effect is allowed, only what is currently installed and by whom.
- **Why a crate (not a module):** criterion 1 — the installation-lifecycle record authority plus manifest grammar, consumed by 7 crates today, with a real CAS-mutated persistence adapter (`installations.rs`) that a module inside `extension_host` would smuggle kernel-adjacent state ownership into.

- **Open questions:** none from PROPOSAL §12.10 — `installations.rs`' further internal decomposition is explicitly named "optional follow-up, not target requirement," not an unresolved decision.

### `crates/extensions/packages/` — directory rules for non-crate packages

Every installable extension's manifest, prompts, schemas, code, and WASM sources live under one `packages/<name>/` directory — the self-containment rule stated in "What belongs here" above. Not every package earns a crate: the package⇒crate rule (§5) draws the line at a channel adapter (binary-only linking) or a heavy/isolated native dependency. Ten of the twelve packages under `packages/first_party/assets/` today fail that test on purpose and stay directories-with-assets: `github`, `gmail`, `google-calendar`, `google-docs`, `google-drive`, `google-sheets`, `google-slides`, `nearai-mcp`, `notion-mcp`, `web-access` (verified, `crates/ironclaw_first_party_extensions/assets/`) — their shared native tool executors (where they have native, non-WASM behavior — `gsuite/`, `coding/`, `web_access.rs`, `skills.rs`) live as modules inside `ironclaw_first_party_extensions` itself, exactly as the rule prescribes. The **excluded WASM-source packages** are a real artifact boundary within the family: `github`, `google-docs`, `google-drive`, `google-sheets`, `google-slides`, and `slack` each carry a `<package>/wasm-src/` directory with its own `Cargo.toml` declaring an empty `[workspace]` table (verified this session — e.g. `crates/ironclaw_first_party_extensions/assets/github/wasm-src/Cargo.toml`) — the standard Cargo idiom for opting a nested manifest out of the parent workspace entirely. These six build via `scripts/build-wasm-extensions.sh` (`cargo component build --target wasm32-wasip2`, prerequisites `cargo-component` + the WASI targets) and ship as committed `.wasm` binaries loaded through `include_bytes!` in `ironclaw_first_party_extensions`. **A named constraint, not yet guarded** (§12.8): there is no `build.rs` freshness check between the committed `.wasm` and its `wasm-src`, so a stale binary ships silently if source changes without a rebuild; "a digest check comparing committed `.wasm` to `wasm-src` source hash is the cheap guard to add." The **package-shape check** (§11.2.10) is the family-wide backstop: every `packages/<ext>/` directory must have a manifest whose declared surfaces are consistent with its crate (if any) and its assets — closing the gap where a package's code and its declared capabilities silently drift apart.

## Family AGENTS.md obligations

Per §11.4, `crates/extensions/AGENTS.md` is written when the family directory is created and must carry, verbatim or by direct reference:

- **The unified extension model recap** — extension is the only installable product object; surfaces are `tool`/`channel`/`auth`; `VendorId` is a credential authority, never product identity; at most one channel surface per extension; runtime kind is a loading mechanism, never taxonomy (invariant #9) — so an agent adding a package never reaches for a `kind` field to express what should be a manifest surface declaration.
- **The package-directory self-containment rule** and **the package⇒crate rule**, both restated verbatim from this document's "What belongs here" section, so "does this need a crate?" is answered the same way every time a new vendor is added.
- **The four-responsibility map** — vocabulary (`contracts/extension_contracts`, outside this family), registry/records (`ironclaw_extensions`), generic hosting (`ironclaw_extension_host`), product-side management (`ironclaw_extension_manager`), concrete packages (`packages/*`) — as a one-line lookup table, so "where does this code go" is a table lookup rather than a re-derivation.
- **The vendor-name rule** — vendor identifiers, protocol branches, and vendor-specific behavior are legal *only* under `packages/*`; the specificity scanner's shrink-only allowlist is the mechanical enforcement, and this family's AGENTS.md must warn that adding to that allowlist (rather than fixing the leak) requires the same review scrutiny as widening a security boundary.
- **The §12.1(c) ordering warning**, restated as an operational checklist item: any change that touches `extension_host`'s dependency on `product` must land the corresponding `product_contracts`/`extension_contracts` port move first, in a separate, independently-landable change — never combined with the layer-metadata edit in the same PR.
