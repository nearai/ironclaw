# Family: `crates/lanes/` — execution mechanisms

**Layer(s):** `runtimes` (all four crates) · **Crates (target):** 4 — `ironclaw_wasm`, `ironclaw_wasm_limiter`, `ironclaw_mcp`, `ironclaw_sandbox` (NEW, by merging `ironclaw_process_sandbox` + `ironclaw_host_runtime`'s `sandbox_process` module + `ironclaw_scripts`) · **Security posture:** deny-by-default execution mechanisms that receive only sealed, already-authorized work and host-mediated services — a lane can fail closed, but it can never authorize itself more than the kernel already granted, and it never holds an ambient network, secret, or filesystem handle of its own.

*Authority: PROPOSAL.md §6.6 (family role + all four crate entries), §2.3/§2.6 (dead-surface findings), §5 (tree), §7/§8 (trust walkthrough + dependency model), §9 rows 42–46, §12.4/§12.10 (risks). CURRENT-state citations are to this session's read of `dde662d5a`.*

## Identity — what this family IS

`crates/lanes/` is PROPOSAL §6.6's execution-mechanism family: "how an *already-authorized* invocation runs." Every lane receives work only after it has crossed the kernel membrane (§7's **T5**) carrying a sealed `Authorized` witness already bound to exactly one `RuntimeLane` — a closed, four-variant enum (`FirstParty`, `Wasm`, `Mcp`, `Process`; `ironclaw_host_api::lane.rs:70-80`, generated by a `runtime_lanes!` macro with a completeness-checked `ALL` array) selected once by `runtime_policy` planning and never re-derived inside the lane. A lane's job is narrow by design: load or connect to the already-selected execution mechanism, run the request under mediated services (narrowed mounts, one-shot staged secrets, policy-scoped egress), and hand back a normalized outcome or a bounded failure class. Nothing here decides whether work is allowed; that decision was already made and sealed before the lane ever saw the request. CURRENTLY this is 5,881 lines across three crates plus a fourth crate's worth of currently-scattered, currently-unwired sandbox machinery (`ironclaw_wasm` 1,613 across 9 files, `ironclaw_wasm_limiter` 163 in 1 file, `ironclaw_mcp` 2,475 in 1 file); TARGET adds a fourth crate, `ironclaw_sandbox`, assembled entirely from parts that already exist today but are split across `ironclaw_process_sandbox`, `ironclaw_host_runtime::sandbox_process`, and `ironclaw_scripts` — net effect on lane *behavior*: none (see that crate's entry).

## What makes it distinct

- **vs `kernel/`:** `kernel/` *decides* — trust ceiling, default-deny grant matching, exact-invocation approval, obligation preparation, and the sealed `Authorized` witness are all kernel work (`ironclaw_capabilities`, `ironclaw_authorization`, `ironclaw_approvals`, `ironclaw_host_runtime`). `lanes/` *executes* what the kernel already decided and can only refuse to run — an unconfigured lane fails closed, verified live today in `RuntimeLane::Process`'s case (see `ironclaw_sandbox` below) — never grant itself additional authority. The line: kernel is authorized-*before*; lanes are executed-*after*, and the witness crossing the boundary between them is sealed precisely so a lane cannot forge or widen it.
- **vs `extensions/`:** `extensions/` owns what an installable *package* **is** — its manifest, registry entry, and installation record (`ironclaw_extensions`), plus vendor-specific `ChannelAdapter`/`ToolAdapter` behavior (`extensions/packages/*`). `lanes/` owns **how** code of a given `RuntimeKind` actually executes — a wasmtime store, an MCP JSON-RPC client, a Docker container — regardless of which package asked for it; a lane has no notion of "Slack" or "Discord," only "WASM component" or "MCP server." The line: extensions is the package naming a `runtime.service`; lanes is the mechanism that name resolves to, shared across every package that picks it.
- **vs `loop/`:** `loop/` hosts **replaceable agent strategy** — the userland code deciding what capability to invoke next — behind `loop_contracts` ports, with `ironclaw_agent_loop` holding a special contracts-only dependency rule precisely because it is not trusted with authority. `lanes/` executes **already-decided, already-authorized** invocations; a lane never sees "why," only "run this, under these mediated services, and report back." The line: loop chooses (untrusted, replaceable); lanes run what was chosen (trusted mechanism, closed set) only after the kernel — never the loop — has authorized it.

## What belongs here / What must never be here

**Belongs:** runtime loading, isolation, and metering for exactly the four `RuntimeLane` variants; normalized outcomes and bounded, host-visible failure classes; the vendor SDKs a lane's *own* protocol genuinely requires (`wasmtime`/`wasmtime-wasi` for the WASM lane, `bollard` for the Docker-backed sandbox lane) — never a vendor SDK for something the lane merely dispatches to.

**Must never be here:** authorization, approval, or trust-policy logic of any kind; ambient network or secret access — every credential and every egress path arrives by injection from `ironclaw_host_runtime`, never as a lane-owned client or store; product behavior or presentation; a second, parallel lifecycle or supervisor (process lifecycle authority is `ironclaw_processes`' job, in `kernel/`); vendor/product names (a lane executes "WASM" or "an OS process," never "the GitHub tool" or "Slack").

## Dependency direction

Every lane depends on `ironclaw_host_api` and, where it touches extension-declared surface data, `ironclaw_extension_contracts` — never the `ironclaw_extensions` registry crate itself, dissolving the `mcp → extensions`/`scripts → extensions` `W7` exceptions (`reborn_dependency_boundaries.rs:3609,3623`, both confirmed live in `LAYER_MATRIX_EXCEPTIONS`). `ironclaw_wasm` additionally depends on its sibling `ironclaw_wasm_limiter`. Mediated services (secrets, network, filesystem, resources) arrive **by injection** from `ironclaw_host_runtime` at construction time — a lane never adds `ironclaw_secrets`, `ironclaw_network`, or `ironclaw_filesystem` as a `Cargo.toml` dependency; the one narrow exception is `ironclaw_resources`' vocabulary, which PROPOSAL directs toward `host_api::resource` rather than a crate-level dependency (see `ironclaw_mcp`'s entry). `ironclaw_wasm_limiter` is also consumed from outside this family, by `ironclaw_hooks` (loop family, layer `loops`) — legal under the layer ladder (`runtimes < loops`) even though PROPOSAL §8.1's family-level dependency diagram only draws the primary `lanes → contracts`/`lanes → wasm_limiter` edges; §8.1's own reading rule states the family picture is a non-exhaustive projection and the matrix, not the picture, is what CI checks. Nothing in `kernel/` is a normal dependency of any lane; the relationship inverts — `kernel/ironclaw_host_runtime` depends on the lanes and selects among them through its closed `RuntimeLaneExecutor` (`runtime_adapters.rs`).

## Security & authority role

Lanes are where PROPOSAL §7's **T6 → T7** transition physically happens: `host_runtime`'s closed lane executor selects a lane by the sealed witness — an unconfigured lane always fails closed, verified in `RuntimeLane::Process`'s current production shape (`runtime_adapters.rs:303,329-332`) — hands the lane narrowed mounts and one-shot staged secrets (TTL'd `take()`, never a store or raw value), and the lane executes under those grants alone. On return, `host_runtime` — never the lane — applies redaction/output-limit/leak checks before anything becomes model-visible or durable evidence (**T7**). The WASM lane makes "mediated services only" mechanical rather than aspirational: its host-import surface is a set of traits with **only `Deny*` implementations available by default** — `DenyWasmHostHttp` (`host.rs:63`), `DenyWasmHostWorkspace` (`:576`), `DenyWasmHostSecrets` (`:589`), `DenyWasmHostTools` (`:602`) — so a WASM component gets exactly the host capabilities Reborn composition explicitly wires and nothing by omission. The sandbox lane's own design documents hold the sharpest version of this story: `.claude/rules/safety-and-sandbox.md` states "the only real containment for an OS process is the sandbox it runs in," motivated by issue #6170 — a shipped cross-tenant file-disclosure bug from a process spawn that bypassed sandbox containment — and requires a served multi-user deployment to fail closed to "no shell" rather than silently downgrade to an unsandboxed host process.

## Family AGENTS.md obligations

Per §11.4, `crates/lanes/AGENTS.md` states the lane contract from PROPOSAL §6.6 verbatim: accept only a canonical, already-authorized invocation; use mediated services exclusively, never an ambient client or store; return a normalized outcome or a bounded failure class; never run a parallel or independent lifecycle. It also states the closed-lane-set rule: `RuntimeLane` (`ironclaw_host_api::lane.rs`) is a closed, macro-generated enum with an `ALL` completeness array — adding a lane is a contract change reviewed as one, never a registry entry a lane crate adds on its own. Concrete guidance-file gaps this pass fixes, verified this session: `ironclaw_wasm_limiter` has no guidance file at all; the merged `ironclaw_sandbox` inherits a `CLAUDE.md` from `ironclaw_process_sandbox` but needs an `AGENTS.md` (the opposite gap from most crates in this repo); `ironclaw_scripts`' own `CLAUDE.md:8` currently tells readers dispatch selection lives "in `ironclaw_dispatcher`" — already-stale guidance pointing at a zero-consumer crate this proposal deletes (§2.6) — corrected in the same merge rather than carried forward.
