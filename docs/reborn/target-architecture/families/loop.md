# Family: `crates/loop/` — the loop-hosting tier

**Layer(s):** `loops` (all four target crates; `ironclaw_runner` re-layers in from `kernel`, `ironclaw_hooks` re-layers in from `substrates` — `ironclaw_agent_loop` and `ironclaw_loop_host` already declare `layer = "loops"` today, verified in each crate's `Cargo.toml`) · **Crates (target):** 4 — `ironclaw_agent_loop`, `ironclaw_loop_host`, `ironclaw_runner` (narrowed), `ironclaw_hooks` (moved layer) · **Security posture:** owns zero authority of its own — a shipped loop is not trusted, and every privileged effect this family wants crosses a `loop_contracts` port into `kernel/`; this family's own decorators (hook middleware, capability-surface filters, the subagent-spawn port) may only narrow or observe what the kernel already granted, never mint or expand it.

## Identity — what this family IS

`crates/loop/` is the replaceable agent-behavior tier and the adapters that host it: the sealed strategy framework that decides what a turn does next (`ironclaw_agent_loop`), the concrete implementations of the ports that framework calls into kernel-mediated services through (`ironclaw_loop_host`), the trusted control-plane adapter that claims kernel-scheduled work and drives a loop against it (`ironclaw_runner`), and the trust-tiered before/after-fact hook middleware that wraps every port call (`ironclaw_hooks`). PROPOSAL §6.7's family role states it in one line: "replaceable loop userland and the adapters that host it. Nothing here is trusted with authority: everything privileged crosses `loop_contracts` ports into the kernel." `docs/reborn/contracts/kernel-boundary.md §4` is the load-bearing contract this family exists to satisfy from the other side of the membrane: "A loop is not trusted because the project shipped it... The kernel secures the loop environment; it does not rely on the loop to preserve kernel invariants." Today the four crates' ports are typed against `ironclaw_turns::run_profile` (11 `Loop*Port` traits plus `AgentLoopDriver`/`AgentLoopDriverHost`, `crates/ironclaw_turns/src/run_profile/{compaction.rs,driver.rs,host/*.rs}`, ~14.3k lines, its own `CLAUDE.md`); the target carves that whole tier out into `contracts/ironclaw_loop_contracts` so this family depends on a thin, host-runtime-free port set instead of reaching through the turn kernel to get it (§6.1.4).

## What makes it distinct

- **vs `kernel/`** — userland vs authority. `docs/reborn/contracts/kernel-boundary.md §3` names agent-loop strategy, prompt assembly, routine/mission orchestration, skill selection, and reference-loop implementations as explicitly **not** kernel; this family is exactly that list. Invariant #12 (PROPOSAL §3) is the rule stated from this side of the fence: "A shipped loop or first-party extension does not bypass capability mediation — first-party raises a policy ceiling, never grants permission." Concretely: `ironclaw_agent_loop`'s executor cannot see a `CapabilityHost` handle, a filesystem client, a secret, or a network transport — it sees only the 11 `Loop*Port` traits (target: `loop_contracts`), and every one of those ports is implemented by a crate in *this* family or in `kernel/`, never inline in the executor.
- **vs `contracts/` (specifically `ironclaw_loop_contracts`)** — ports are defined there, implemented here. The distinction is a one-way rule with a name: `agent_loop` calls `Loop*Port` methods, `loop_host`/`runner`/`hooks` implement them by wrapping kernel services (`ironclaw_capabilities`, `ironclaw_host_runtime`) or by decorating another implementation (hooks wraps the base port; capability-surface filters wrap the base port; the subagent-spawn port wraps the base port). Nothing in `contracts/` may implement its own ports — that would collapse the membrane it exists to enforce.
- **vs `product/`** — conversation/binding/admission UX vs strategy execution. The two upward edges this family has *today* are both single, data-only symbols, and both are being cut: `ironclaw_product`'s only import from `ironclaw_runner` is the failure-summary formatter set (`product/src/projection/turn_events.rs:34`; `ironclaw_product`'s own tests additionally `include_str!` a runner source file, an accidental coupling with no proposal-side successor), and its only import from `ironclaw_loop_host` is the `FAILURE_EXPLANATION_SYSTEM_PROMPT` constant (`loop_host/src/lib.rs:988` equivalent). PROPOSAL §6.9.1 resolves both by relocating the *data*, not by keeping the edge: the failure-summary tables join `host_api::failure` (already a 166-line module, `crates/ironclaw_host_api/src/failure.rs`) and the prompt constant becomes "a product-owned prompt asset." After the move, `product/` depends on nothing in `loop/` for behavior — it only ever *reads a claimed run's* projected state.

## What belongs here / What must never be here

**Belongs:** the sealed strategy/executor framework and its resumable state; host-port adapter implementations over kernel services; the claimed-work control plane (driver registry, claim/lease loop, loop-exit application); trust-tiered hook middleware wrapping the port set. **Must never be here** (drawn from each crate's own `CLAUDE.md`/`CONTRACT.md`, verified verbatim this session): product-specific logic or product adapters (`agent_loop/CLAUDE.md`); provider clients, dispatcher internals, product binding, or DB migrations (`loop_host/CLAUDE.md`); planner strategy slots exposed through Reborn APIs, or silent fallback from a planned to a text-only driver without an explicit profile/readiness decision (`runner/CLAUDE.md`); extension bundle loading/installation authority, or the runner-facing `AgentLoopDriver` trait itself (`hooks/CLAUDE.md` — that stays in the contracts tier). Loop state stores refs, cursors, counters, versions, and safe summaries only — never raw prompts, raw model output, tool args, secrets, host paths, provider errors, or stack traces (`agent_loop/CLAUDE.md`, restated identically for hook-visible output in `hooks/CLAUDE.md`'s non-negotiable invariants).

## Dependency direction

`loop/` crates depend on `contracts/` (`host_api`, `common`, and — once carved out — `loop_contracts` for the port set) and, for the host-adapter and control-plane crates, on `kernel/` siblings whose services they wrap (`capabilities`, `host_runtime`, `resources`, `turns`) and on `domains/` crates their adapters need (`safety`, `skills`, `memory`, `threads`, `llm`, `events`). `ironclaw_agent_loop` alone keeps the stricter special rule the matrix already carries at `reborn_dependency_boundaries.rs:129`: contracts-layer deps only — no kernel, no domains, no host runtime. `loop/` crates may never depend on `products/` or `app/` (§8.2's forbidden-edge matrix, `loop` row: "✗ products"), and `contracts/ironclaw_turns` must never depend on `ironclaw_hooks` — an absence the architecture suite proves directly (`hooks/CLAUDE.md`: "Architecture test in `ironclaw_architecture::tests::reborn_dependency_boundaries` proves the `ironclaw_turns -> ironclaw_hooks` edge stays absent").

## Security & authority role

Two trust transitions from PROPOSAL §7 bracket this family on both sides, and neither one is implemented inside it. **T4 — queued work → claimed execution** (`processes`/`runner`): a lease claim with heartbeat and terminal lease-expiry (no auto-retry of side-effecting work); the loop receives only `loop_contracts` ports scoped to the one claimed run — never an ambient handle to any other run's state. **T5 — loop request → authority decision** (`capabilities`, in `kernel/`): trust ceiling → default-deny authorization → exact-invocation approval → obligations → the sealed `Authorized` witness, none of it constructible from this family. Loop exits are treated as **claims, not truth**: `LoopExitApplier` (kernel-owned, in `ironclaw_turns`) validates host-minted evidence refs before any durable transition commits, so a compromised or buggy loop cannot forge a successful outcome by simply asserting one. Inside the family, `ironclaw_hooks`' own non-negotiable invariants (verified verbatim, `hooks/CLAUDE.md`) state the ceiling precisely: hooks cannot grant authority; cannot bypass authorization, approvals, runtime policy, resource policy, secrets policy, filesystem policy, or network policy; cannot receive ambient secrets, filesystem handles, network clients, process handles, or raw runtime authority; `Gate`/`Mutator` decisions fail closed, `Observer`/`Effect` decisions fail isolated with redacted audit; and a hook that demonstrates a protocol violation (timeout, panic, malformed decision) gets its slot poisoned for the rest of the current turn run. The `TurnRunTransitionPort` trait (`ironclaw_turns::runner`, `turns/src/runner.rs:137`) is the one kernel-transition-shaped seam this family must not implement from its host-adapter crate — `loop_host`'s own guardrail already says so (`loop_host/CLAUDE.md`: "Do not make adapters perform runner state transitions"), which is exactly why its current `EventPublishingTurnRunTransitionPort` decorator (`loop_host/src/turn_event_publisher.rs`, 384 lines) sheds to the `turns`/`runner` seam in the target (§6.7.2).

This one edit legalizes the standing `hooks → wasm_limiter` W6 exception ("directory re-layout verifies runtime/substrate placement," per `reborn_dependency_boundaries.rs:3516-3648`) — `loops` may depend on `runtimes`, where `ironclaw_wasm_limiter` lives, under the monotone ladder; `substrates` may not.

- **Must never contain:** the runner-facing `AgentLoopDriver` trait (stays in the contracts tier); concrete `LoopCapabilityPort`/`LoopPromptPort`/`LoopModelPort` *base* implementations (those stay `loop_host`/`runner` — hooks only decorates); extension bundle loading/installation authority ("Installed-tier WASM hooks execute here once their module bytes are resolved, but the extension installer remains the authority for sourcing those bytes," `hooks/CLAUDE.md`).
- **Allowed internal deps:** `ironclaw_events`, `ironclaw_host_api`, `ironclaw_prompt_envelope`, `ironclaw_loop_contracts` (replacing today's `ironclaw_turns`), `ironclaw_wasm_limiter` (legal once the layer flips).
- **Forbidden:** `ironclaw_turns` must never depend on `ironclaw_hooks` (architecture-tested, absence proven directly); no `product`, `extension_host`, or `dispatcher` edges.
- **Public contracts & ports:** `HookDispatcher` with its tier-specific `install_builtin_*`/`install_trusted_*`/`install_installed_*` methods; `HookRegistry`; the predicate DSL types; implements the full `loop_contracts` `Loop*Port` set as the `HookedLoop*Port` decorator layer, deliberately colocated with the dispatcher it wraps.
- **Security & authority role:** significant, and precisely bounded — hooks cannot grant authority or bypass any kernel-mediated policy stage, cannot receive ambient secrets/filesystem/network/process handles, and route every side effect through existing `HostRuntime`/capability dispatch paths; `Gate`/`Mutator` fail closed, `Observer`/`Effect` fail isolated with redacted audit; a protocol-violating hook is slot-poisoned for the rest of the run (all verbatim, `hooks/CLAUDE.md`'s non-negotiable invariants). Trust class is fixed by *source*, never by manifest claim — the loader, not the type system, is responsible for matching the correct tier-specific installer to a hook's actual origin, and the crate's own docs name this as the one thing the type system cannot enforce.
- **Why a crate (not a module):** an independent trust-tier contract with its own wasmtime cone (`wasm/runtime.rs`, isolated from `loop_host`/`runner`'s non-wasm adapters) and exactly 2 consumers (`runner` installs, `composition` loads) — folding it into either would either give the hook engine's wasmtime dependency to every `loop_host` consumer or give `runner`'s non-wasm adapters an unwanted wasmtime cone.
- **Enforcement:** `reborn_dependency_boundaries.rs`'s proof that the `ironclaw_turns -> ironclaw_hooks` edge stays absent; the loader-contract regression guard `tier_specific_installers_are_documented_as_loader_contract` in `dispatch.rs`; the cross-run isolation test `per_build_dispatcher_state_does_not_leak_across_runs` plus its shared-state-baseline counterpart `legacy_with_hook_dispatcher_shares_state_across_builds` (both `crates/ironclaw_runner/tests/hooks_integration.rs`); `cargo test -p ironclaw_hooks` (plus its `integration` feature for the folded-in multi-host adversarial suite); `cargo test -p ironclaw_architecture`.
- **Open questions (PROPOSAL §12.10):** trigger/hook SQL convergence vs. an ADR — `hooks`' folded-in `libsql_backend`/`postgres_backend` (~1.7k lines of hand-written SQL) is one of only two family-wide exceptions to the `ScopedFilesystem` persistence idiom (the other is `domains/ironclaw_triggers`); the proposal deliberately leaves "converge on the filesystem fabric or write the ADR" unresolved (§12.6, cross-referenced from §6.7.4).

## Family AGENTS.md obligations

Per §11.4, `crates/loop/AGENTS.md` is written when the family directory is created and must carry, verbatim or by direct reference:

- **The loop trust story** — "a shipped loop is not trusted; ports are the membrane," restated from `kernel-boundary.md §4` and invariant #12, so an agent editing any of the four crates starts from the same non-negotiable premise `agent_loop/CLAUDE.md` and `hooks/CLAUDE.md` already state independently today.

- **The port-implementer census rule** — this document's "Dependency direction" section *is* the sanctioned decorator chain; a new `Loop*Port` implementation anywhere in the workspace must be added to that list in the same change, and §11.2.4's mechanical scan is what catches an addition that skips the census.
- **The before-adding-a-crate gate** (invariant #13 applied here) — a fifth crate in this family must name its own pipeline stage (T4/T5 boundary role) and its own multi-impl port or trust seal; none of the four crates here were merged or split by this proposal, which is itself evidence the existing four each already earned their boundary.
- **The dependency-direction rule restated as a check** — `loop/` may depend on `contracts/`, `domains/`, and `kernel/`; `loop/` may never depend on `products/` or `app/`; `contracts/ironclaw_turns` (post-split, the turn-admission kernel crate) must never depend back into this family.
