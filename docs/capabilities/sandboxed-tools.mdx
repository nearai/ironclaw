WASM tools run inside a WebAssembly sandbox powered by [wasmtime](https://wasmtime.dev/). A module gets nothing by default — no filesystem, no network, no environment, no processes. Everything it can reach is declared in its extension's `manifest.toml` and granted by the host, per call.

This is IronClaw's recommended approach for custom integrations that need stronger isolation than a built-in Rust tool provides.

---

## How It Works

```
model selects a tool
    ↓
authorization reads the manifest and plans obligations for this call
  (network policy, one-shot credential staging, resource ceilings)
    ↓
host loads the module and instantiates it with a fuel + memory budget
    ↓
tool code runs and calls http-request with an UNAUTHENTICATED request
    ↓
host egress boundary
  ├─ reject tool-supplied Authorization / Cookie / x-api-key headers
  ├─ match scheme + host against the tool's network_targets
  ├─ leak-scan URL, headers, body
  └─ inject the staged credential
    ↓
external service
    ↓
host response boundary — strip sensitive headers, redact, leak-scan
    ↓
response returns into the sandbox
    ↓
tool output returns to the model
```

The credential never enters the sandbox. See [Secrets & Sandboxing](/security/secrets-and-sandboxing) for that flow in detail.

## Sandbox Limits

Every execution is bounded by three limits applied at instantiation:

| Limit | Default | Behavior on breach |
|-------|---------|--------------------|
| Fuel | 500,000,000 instructions | The module is terminated the moment it runs out. Prevents infinite loops and runaway computation. |
| Memory | 10 MB linear memory | An allocation beyond the cap traps and terminates the module. |
| Wall clock | 60 seconds | Execution is interrupted via wasmtime's epoch deadline. |

These are host-side defaults, not environment-tunable knobs — there is no `WASM_FUEL_LIMIT`-style variable. A deployment that needs different bounds configures them where the runtime is composed.

Two further per-execution budgets apply to host calls: logging is capped at 1,000 entries per execution and 4 KB per message, and an HTTP request defaults to a 30-second timeout (a tool may pass its own, capped at the execution deadline).

Per-call egress size is bounded by the manifest's `max_egress_bytes`, and output size by the resource ceiling authorization attaches to the call.

## The Manifest

Every extension ships a `manifest.toml` (schema `reborn.extension_manifest.v3`) alongside its `.wasm` module. This file is the single source of truth for what the extension's tools may do, and it is what you are approving when you install.

```toml
schema_version = "reborn.extension_manifest.v3"
id = "github"
name = "GitHub"
version = "0.2.8"
description = "GitHub repository, issue, and pull request capabilities."
trust = "first_party_requested"

[runtime]
kind = "wasm"
module = "wasm/github_tool.wasm"

[[tools]]
id = "github.create_repo"
description = "Create a GitHub repository."
effects = ["network", "use_secret", "external_write"]
default_permission = "ask"
visibility = "model"
origin_gate_matrix = { loop_run = "gated_unless_granted", product = "forbidden", automation = "forbidden" }
input_schema_ref = "schemas/github/create_repo.input.v1.json"
prompt_doc_ref = "prompts/github/create_repo.md"

network_targets = [
  { scheme = "https", host_pattern = "api.github.com" },
]
max_egress_bytes = 10485760

[[tools.credentials]]
handle = "github_runtime_token"
vendor = "github"
audience = { scheme = "https", host = "api.github.com" }
injection = { type = "header", name = "authorization", prefix = "Bearer " }
```

### `[runtime]`

`kind` is `wasm`, `mcp`, or `first_party` — implementation detail, not taxonomy. For `wasm`, `module` is the path to the compiled component within the package.

### `[[tools]]`

| Field | Meaning |
|-------|---------|
| `id` | Namespaced tool id (`<extension>.<tool>`). |
| `effects` | Effect classes claimed by this tool: `network`, `use_secret`, `external_write`, `read_filesystem`, `write_filesystem`, `spawn_process`, `financial`, and others. Authorization plans obligations from these. |
| `default_permission` | `allow`, `ask`, or `deny`. `ask` pauses the call for user approval. |
| `visibility` | Whether the tool is offered to the model at all. |
| `origin_gate_matrix` | Per-origin reachability — `loop_run` (an agent turn), `product` (a direct product action), `automation` (an unattended trigger). A tool can be reachable from a supervised turn and `forbidden` from a scheduled run. |
| `network_targets` | Allowed outbound destinations by `scheme` and `host_pattern`. Unlisted destinations are refused before the connection opens. |
| `max_egress_bytes` | Per-call ceiling on outbound bytes. |
| `input_schema_ref` / `prompt_doc_ref` | Paths to the JSON Schema for parameters and the model-facing prompt doc. |

### `[[tools.credentials]]`

| Field | Meaning |
|-------|---------|
| `handle` | The credential's name in the secret store. |
| `vendor` | The credential authority namespace (`google`, `github`, …), which may be shared across extensions. |
| `audience` | The `scheme` + `host` this credential may be attached to. A credential declared for one host is never sent to another. |
| `scopes` | For OAuth credentials, the scopes required by this specific tool. |
| `injection` | How the host attaches it: `header` (with optional `prefix`), `query_param`, `path_placeholder`, or `body_json_pointer`. |

There is no manifest field that lets a tool *read* a secret. Credential material is only ever attached by the host to a request the host has already validated.

## Host Functions

The WIT interface (`near:agent@0.3.0`) declares six host functions. The production host starts deny-all and grants three:

| Function | Available in production | Notes |
|----------|------------------------|-------|
| `log(level, message)` | Yes | Collected and emitted after execution. 1,000 entries max, 4 KB per message. |
| `now-millis()` | Yes | Milliseconds since the Unix epoch. |
| `http-request(method, url, headers-json, body, timeout-ms)` | Yes, when a network policy is staged | The entry point for the credential-injection flow. Denied outright when the call has no staged policy. |
| `workspace-read(path)` | No | Denied by the production host. |
| `secret-exists(name)` | No | Denied by the production host. Returns a boolean, never a value, even where granted. |
| `tool-invoke(alias, params-json)` | No | Declared for future chained tool calls; denied today. |

That is the entire surface. A WASM tool cannot call arbitrary OS functions, spawn processes, open files, or reach the network except through `http-request`.

The tool side of the interface is three exports: `execute(request) -> response`, `schema() -> string` (a JSON Schema for the tool's parameters), and `description() -> string`.

## Tool Discovery

Tools reach the agent as **extension packages**. Each package is a directory under the
runtime's `/system/extensions/<extension-id>/` root containing a `manifest.toml` that
declares the tools it provides, alongside the compiled `.wasm` module.

`ironclaw extension search` lists the packages the runtime can see.

---

## Installing WASM Tools

```bash
# Find an available package
ironclaw extension search my-tool

# List every package the install knows about
ironclaw extension search

# Install one by id
ironclaw extension install my-tool
```

`extension install` takes an **extension id** from `extension search` — never a file path
or a URL. Passing `./my-tool.wasm` or an `https://` URL fails.

To add a package you built yourself, import the packaged archive from **Extensions** in
the [web interface](/using/webui). That is the supported path for getting a new package
into the runtime; once it's there, `extension search` lists it and you install it by id.

---

## Module Compilation and Caching

Modules are compiled by wasmtime on first load and the prepared module is cached in the running process, keyed by module path. Only the first invocation after a restart pays compilation cost; there is no on-disk compiled-artifact cache.

## Security Notes

<Warning>
Read the manifest before installing an extension from an untrusted source — specifically `network_targets`, `credentials`, `effects`, and `default_permission`. Those four fields are the whole of what you are granting.
</Warning>

<AccordionGroup>
  <Accordion title="Credential injection is one-way" icon="lock">
    The host attaches credentials to outgoing requests. There is no host function that returns secret material, and production egress accepts only credentials staged one-shot by authorization for that exact call. A compromised module still cannot read the secret store.
  </Accordion>

  <Accordion title="Tool-supplied auth headers are refused" icon="ban">
    A request carrying `Authorization`, `Cookie`, `x-api-key`, or a `user:pass@` URL from the tool is rejected at the egress boundary before it is sent — so a module cannot bypass the injection path by constructing its own credentials.
  </Accordion>

  <Accordion title="No process spawning" icon="shield">
    Modules cannot spawn child processes, execute shell commands, or load dynamic libraries. The interface exposed to a module is the six functions above and nothing else.
  </Accordion>

  <Accordion title="Fuel prevents denial-of-service" icon="zap">
    A buggy or malicious module that enters an infinite loop is terminated when it exhausts its fuel budget, and again at the 60-second epoch deadline. A single tool cannot block the agent indefinitely.
  </Accordion>
</AccordionGroup>
